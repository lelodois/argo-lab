Argo CD na prática

O reconciliador que faz deploy na Cora — explicado pelos SEUS pipelines: o chart cora-v5.x, o wait-app-stage, o plugin do gocdnext e o incidente do Rollout preso em Progressing.

1. A ideia central: reconciliação, não script

Deploy tradicional é imperativo: o CI roda kubectl apply e torce. Argo CD inverte: o Git é o estado desejado, o cluster é o estado real, e um controlador roda em loop comparando os dois. Divergiu? Ele converge (ou avisa). O CI nunca toca o cluster — só muda o desejo.

flowchart LR
  CI["CI (gocdnext)\nbuilda + pusha imagem"] -- "app set image.tag=1.301.9fb5ab0" --> APP
  GIT["Git / Helm chart\n(estado desejado)"] --> APP["Application\n(o objeto Argo)"]
  APP -- "render (helm template)" --> MANIF["Manifests desejados"]
  MANIF -- diff --> K8S["Cluster\n(estado real)"]
  K8S -- "sync (aplica o delta)" --> K8S

Consequências práticas: drift feito na mão no cluster aparece como OutOfSync (e com selfHeal é desfeito sozinho); rollback é voltar o desejo, não desfazer comandos; e o deploy sobrevive a CI fora do ar — o Argo continua reconciliando.

2. O objeto de tudo: a Application

Cada app×ambiente é um objeto Application (ex.: engineering-metrics-stage, credit-card-statement-production). Ele aponta:

  • source — repo/chart + parâmetros. Na Cora: o chart cora-v5.x renderizado por um config-management plugin (CMP) que recebe HELM_ARGS — é por isso que o deploy faz app set --plugin-env HELM_ARGS="--set global.image.tag=…";
  • destination — cluster + namespace (cora);
  • syncPolicy — manual ou automated (+ prune: apaga o que sumiu do desejo; + selfHeal: desfaz drift manual).

No seu mundo

O deploy da Cora não commita tag em repo de manifests: o CI muda um parâmetro da Application (app set … HELM_ARGS) e o auto-sync reage. Mais rápido, porém o "estado desejado" vive em parte no objeto Application — o argocd app history vira a memória das versões.

3. Os dois eixos de status (decorar isto paga o guia)

EixoValoresPergunta que responde
SyncSynced OutOfSyncO que está no cluster é igual ao desejado?
HealthHealthy Progressing Degraded Suspended/MissingO que está no cluster está funcionando?

São independentes — e as combinações contam histórias diferentes:

  • OutOfSync + Healthy → mudança pendente, versão antiga rodando bem;
  • Synced + Progressing → aplicou, aguardando ficar pronto (pods subindo, probes passando);
  • Synced + Degraded → aplicou e o resultado quebrou (crashloop, probe falhando…).

O seu incidente (01/09)

O wait-app-stage mostrou o Rollout Synced | Progressing por 10 min até o timeout. Tradução: o Argo aplicou certinho — mas o pod novo nunca ficou Ready. A partir daí a investigação sai do Argo e vai pro pod: kubectl describe pod (probe? imagem? recursos?), logs do container. O Argo detecta e reporta; a causa mora no workload.

4. Ordem de aplicação: waves e hooks

Sync não é "aplica tudo de uma vez". Anotações controlam a ordem:

  • argocd.argoproj.io/sync-wave: "-1" — waves menores aplicam primeiro, e a wave seguinte só entra quando a anterior está Healthy. O chart da Cora põe o Job de migration numa wave antes do Rollout: migra, depois sobe o app;
  • argocd.argoproj.io/hook: PreSync|PostSync|Skip — recursos que rodam em volta do sync em vez de fazer parte do estado. (O comentário argocdSkipHook no values da statement existe porque versões velhas do chart marcavam o Rollout com hook: Skip — e aí o Argo nunca o aplicava.)

A armadilha clássica da wave

Se a migration (wave −1) trava — ex.: imagem sumiu do registry → ImagePullBackOff — a wave do app nunca chega e o sync congela em silêncio. Foi o incidente de 17/07 no engineering-metrics: CI verde, prod apontando pra imagem inexistente. O wait-app-stage de vocês existe exatamente pra transformar isso em build vermelho: espera o Job desta revisão aparecer (prova que o app set refletiu) e depois app wait --operation --sync --health com filtro por recurso — Jobs históricos degradados não bloqueiam revisão saudável. Isto também explica a memória do time: "app tem que detectar DATABASE_MIGRATION=true, rodar Flyway e SAIR — senão o Job pendura pra sempre" (Job que não termina = wave que não completa).

5. O ciclo refresh → diff → sync → health

sequenceDiagram
  participant CI as CI (plugin argocd)
  participant Argo as Argo CD
  participant K8s as Cluster
  CI->>Argo: app set (HELM_ARGS: tag nova)
  Argo->>Argo: refresh: re-renderiza o chart
  Argo->>K8s: diff desejado × real → OutOfSync
  Note over Argo: syncPolicy automated dispara
  Argo->>K8s: wave -1: Job migration
  K8s-->>Argo: Job Healthy (Completed)
  Argo->>K8s: wave 0: Rollout, Service, ...
  K8s-->>Argo: Rollout Progressing → Healthy
  CI->>Argo: app wait --sync --health (o gate)
  Argo-->>CI: verde (ou timeout = vermelho)

Refresh ≠ sync: refresh só recalcula o diff (a cada ~3 min, ou forçado); sync é aplicar. Com auto-sync, um segue o outro.

6. CLI de sobrevivência

# estado geral (o "raio-x" — foi o que decifrou o incidente)
argocd app get engineering-metrics-stage            # recursos, sync, health, condições
argocd app get X -o json | jq '.status.resources[]' # versão scriptável

argocd app diff X          # o que mudaria num sync (ótimo pré-deploy)
argocd app sync X          # aplica; --resource filtra escopo
argocd app wait X --operation --sync --health --timeout 600   # o gate de pipeline
argocd app history X       # revisões (deploy id, data, revisão)
argocd app rollback X 3    # volta pro id 3 do history
argocd app set X --plugin-env HELM_ARGS="--set global.image.tag=1.302.abc1234"
