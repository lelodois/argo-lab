A Esteira do Laboratório

Você agora tem, rodando no seu Mac, a mesma máquina de deploy que empresas grandes usam. Esta página explica cada peça, como elas conversam e por quê — sem assumir que você conhece os nomes.

🧩 As peças (e a analogia do restaurante)

Pense num restaurante que promete: "a mesa do cliente sempre igual ao pedido escrito".

📖Git (GitHub: argo-lab) O caderno de pedidos. Está escrito ali: "quero o billing-lab versão v1, 2 cópias, com health-check". Mudar o pedido = fazer um commit. github.com/lelodois/argo-lab
🏭gocdnext (CI) A cozinha. Quando chega pedido novo (push), ela prepara: roda os jobs do pipeline. É o software que a Cora usa, compilado do fonte na sua máquina. http://localhost:3001
🗄️Registry local A despensa. Guarda as imagens Docker prontas (o app empacotado) com etiqueta de versão. localhost:5551
🤵Argo CD O maître obsessivo. Lê o caderno de pedidos a cada 3 min e confere a mesa. Diferente? Ele mesmo arruma. Alguém mexeu na mesa por fora? Ele desfaz. https://localhost:8443
🏢Kubernetes (k3d) O salão. Um mini-datacenter de 2 "máquinas" (containers) onde o app de fato roda. É a mesma tecnologia dos clusters de produção. cluster "argo-lab" no colima
💳billing-lab (o app) O prato servido. Um servidor web pequeno que imita o formato do billing real: tem migração de banco, health-check e sobe em canary. http://localhost:8090

🔗 Como tudo se conecta

flowchart LR
  DEV["👤 Você\ngit push"] --> GH["📖 GitHub\nargo-lab"]
  GH -- "webhook (push)" --> CI["🏭 gocdnext\nserver + agent"]
  CI -- "job: app sync" --> ARGO["🤵 Argo CD\n(no cluster)"]
  CI -- "job: app wait\n(o fiscal)" --> ARGO
  GH -- "lê os manifests" --> ARGO
  REG["🗄️ Registry\nlocalhost:5551"] -- "imagem billing-lab:vN" --> K8S
  ARGO -- "aplica e vigia" --> K8S["🏢 Kubernetes k3d\nnamespace cora"]
  K8S --> APP["💳 billing-lab\nlocalhost:8090"]

Repare no desenho: a cozinha (CI) nunca toca o salão (cluster). Ela só avisa o maître ("sync") e depois fiscaliza ("wait"). Quem toca o cluster é sempre o Argo. Isso se chama GitOps — e é o jeito que a Cora (e meio mundo) faz deploy.

🎬 O que acontece num deploy, passo a passo

1
Você roda make deploy TAG=v2 — builda a imagem do app, empurra pra despensa (registry) e commita a nova versão no caderno de pedidos (muda a tag no manifest) + push.
2
O GitHub avisa o gocdnext (webhook de push). O pipeline deploy acorda com 2 jobs.
3
Job sync: um container do plugin argocd roda argocd app sync billing-lab — "maître, o pedido mudou, confere aí".
4
O Argo aplica em ordem: primeiro o Job de migração (o "arruma a base antes"); só quando ele termina com sucesso o Rollout entra — e em canary: troca 50% dos pods, espera 20s observando, depois troca o resto.
5
Job wait-healthy: argocd app wait --health --timeout 300 — o fiscal. Se o app novo não ficar saudável a tempo, o build fica vermelho. Deploy quebrado nunca passa despercebido.
6
SUCCESS — e curl localhost:8090 mostra a versão nova. Foi exatamente o run deploy #3 que acabamos de ver passar.

🤔 Perguntas de iniciante (as que todo mundo tem)

O que é Kubernetes, em uma frase?

Um sistema que roda suas aplicações em containers e as mantém vivas: se um cai, ele sobe outro; se você pede 2 cópias, ele garante 2 cópias. Você declara o que quer, ele briga com a realidade até chegar lá.

O que é um pod?

A menor unidade que o Kubernetes gerencia: um "envelope" com um ou mais containers. No lab, cada cópia do billing-lab é um pod. kubectl -n cora get pods lista os seus.

O que é GitOps e por que o deploy é um commit?

GitOps = o Git é a única fonte da verdade sobre o que deve estar rodando. Vantagens práticas: histórico (todo deploy é um commit, com autor e hora), rollback barato (git revert), auditoria de graça, e ninguém precisa de acesso direto ao cluster pra deployar.

O que significam Synced e Healthy?

São duas perguntas diferentes que o Argo responde o tempo todo:

  • Synced: "o que está no cluster é igual ao que o Git pede?" (OutOfSync = tem mudança pendente)
  • Healthy: "o que está no cluster está funcionando?" (Progressing = subindo; Degraded = quebrado)

Um app pode estar Synced e Degraded: o Argo aplicou tudo certinho… e o resultado quebrou.

E se eu mudar algo direto no cluster, na mão?

O Argo desfaz. Teste: kubectl -n cora scale rollout billing-lab --replicas=5 — em ~1 minuto volta pra 2. Isso é o selfHeal: mudança que não passou pelo Git não sobrevive. Parece chato, é o que impede o "gato" de 3h da manhã de virar estado permanente que ninguém documentou.

O que é o canary?

Em vez de trocar todos os pods de uma vez, troca metade, espera observando (20s no lab; em prod, minutos + métricas), e só então troca o resto. Se a versão nova estiver quebrada, só metade do tráfego sofreu — e dá pra abortar. O nome vem do canário na mina de carvão.

Pra que serve o "Job de migração" antes do app?

Apps mudam o banco de dados entre versões (nova coluna, nova tabela). O Job roda essas migrações antes do app novo subir — o Argo segura o resto do deploy até ele terminar. E aqui mora um incidente clássico que você já viveu na Cora: se o Job trava (imagem sumida, processo que não sai), o deploy inteiro congela em silêncio. O exercício 5 do lab reproduz isso.

Como faço rollback?

Do jeito GitOps: make conserta (= git revert + push) — o Argo vê o "pedido antigo" de volta e converge. Existe também o argocd app rollback por histórico, mas cuidado: ele desliga o auto-sync (senão o Argo re-aplicaria o Git por cima do rollback).

Qual a diferença entre o gocdnext e o Argo? Os dois não fazem deploy?

Divisão de trabalho: o gocdnext (CI) constrói, testa e decide quando (pipeline, aprovações, gates). O Argo (CD) é quem de fato aplica e mantém o estado no cluster. No lab (e na Cora), o CI só dá dois recados ao Argo: "sync" (aplica) e "wait" (me avisa se não ficar saudável). CI = gatilho e fiscal; Argo = executor e guardião.

Como ligo e desligo o laboratório?
# desligar (libera CPU/RAM)
k3d cluster stop argo-lab
docker compose -f ~/cora/gocdnext/docker-compose.yml stop postgres
pkill -f gocdnext-lab   # server + agent

# ligar de novo
k3d cluster start argo-lab
docker compose -f ~/cora/gocdnext/docker-compose.yml start postgres
(source /tmp/gocdnext-lab/server.env && /tmp/gocdnext-lab/server &)
(source /tmp/gocdnext-lab/agent.env  && /tmp/gocdnext-lab/agent &)
kubectl -n argocd port-forward svc/argocd-server 8443:443 &

⚠️ Os binários e envs vivem em /tmp/gocdnext-lab/ — se o Mac reiniciar e o /tmp limpar, é só recompilar (go build no repo do gocdnext) e recriar os envs.

🧗 As 5 lições do mundo real (os perrengues que enfrentamos montando)

Montar isso não foi apertar um botão — e cada obstáculo foi uma aula de infra corporativa:

1 · Rate limit do Docker Hub. A rede da empresa esgota a cota anônima de downloads (429). Saída: puxar pelas réplicas espelho (mirror.gcr.io) e re-etiquetar localmente.
2 · O proxy corporativo (Netskope) inspeciona TLS. Ele se coloca no meio das conexões seguras com um certificado próprio — e cada camada precisa confiar nele separadamente: a VM do Docker, os nós do Kubernetes e até containers de build. Três instalações da mesma CA.
3 · Programas Go carregam certificados só no boot. Instalar a CA não bastou — foi preciso reiniciar os nós, porque o containerd (escrito em Go) lê o pool de CAs uma vez e nunca mais.
4 · Arquitetura de CPU importa. O plugin argocd publicado só existe pra Intel (amd64); seu Mac é Apple Silicon (arm64). "no matching manifest" = não há versão pro seu processador. Saída: buildar o plugin do fonte, localmente.
5 · Webhook tem assinatura. O gocdnext rejeita webhook sem HMAC — simular um push do GitHub exige assinar o corpo com o segredo combinado. Segurança que parece burocracia até o dia que alguém tenta forjar um deploy.
